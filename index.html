Banking Microservices Architecture

A channel architecture for internet and mobile banking. Domain services own one capability each. A core adapter is the only path to the system of record.

Select a component. Arrows show the request direction, and the connected path is highlighted.

Component

Select a component

Select a component to see its responsibility. Connected components and arrows stay highlighted.

Generic channel pattern for discussion. It is not a private banking environment.

Architecture overview

Channels stay thin. Accounts, payments and beneficiaries are separate services behind one gateway. The core adapter isolates the system of record from those services.

Problem statement

Account enquiry, payments and payee management change at different speeds. One application couples every release to the system of record and makes a channel change harder to isolate.

Design principles

  • One business capability per service.
  • Each service owns its data.
  • Channels call services, not the core.
  • The adapter is the only core contract.
  • A customer action that needs an immediate answer stays a synchronous call.

Components and responsibilities

  • Channels present the journey.
  • The gateway authenticates and routes.
  • Accounts, payments and beneficiaries own their capabilities.
  • Service data stays private to its service.
  • The adapter translates to the system of record.

Request and data flow

A channel call reaches the gateway and is routed to one domain service. That service reads or writes only its own data. When the ledger must be consulted, the service calls the adapter. The adapter returns a result. The channel never holds a core contract.

Technology choices

Java and Spring Boot for the services, REST for the channel contracts, and application security at the edge. This maps the study to the stack I use. It is not a diagram of a specific bank.

Scalability considerations

Stateless services can run as more than one copy behind the gateway, and each service scales with its own traffic. The adapter has to respect the capacity of the system of record, so channel scale does not become unlimited core load.

Security considerations

The gateway is the authenticated entry. Services accept calls that have passed that edge. Customer data stays in the service that needs it. Core credentials stay in the adapter, not in channel code.

Resilience and fault tolerance

A failure in one domain service does not have to remove the others. The gateway can stop sending work to an unavailable service. Calls toward the system of record use a timeout. Payment instructions carry an idempotency key.

Digital Loan Origination System

A reference journey for a home loan or loan against property. One application moves through specialist steps. Each step keeps its own responsibility and its own outcome.

Select a step. Arrows show the journey moving forward, and the connected steps stay highlighted.

Component

Select a component

Select a component to see its responsibility. Connected components and arrows stay highlighted.

Generic origination journey. It does not describe a lender's credit policy or internal integrations.

Architecture overview

The channel enters through one origination API. Onboarding, KYC, property evaluation, credit assessment and disbursement are separate stages. An application record tracks how far the journey has gone.

Problem statement

Those stages are different kinds of work. Folding them into one module hides the handoff, and a change in one stage becomes a change to the whole journey.

Design principles

  • One API for the channel.
  • A stage owns its decision and its data.
  • The application identifier is shared. The database is not.
  • The next stage starts from the previous outcome.
  • Credit policy stays inside credit assessment.

Components and responsibilities

  • Channels start and resume the application.
  • The API opens the journey and routes the step.
  • Each stage records its own outcome.
  • The application record remembers the last completed stage.

Request and data flow

The channel submits to the origination API. Onboarding captures the applicant. KYC records a verification outcome. Property evaluation records the collateral outcome. Credit assessment records the decision. Disbursement records the release step. Each stage reads the application identifier and writes only its outcome.

Technology choices

Java, Spring Boot, microservices and REST, consistent with the origination work on this site. A long-running journey can be coordinated by a workflow component. This study does not assign a specific workflow product to a lender.

Scalability considerations

Stages scale separately. Document-heavy property evaluation does not have to scale the same way as credit assessment. The API stays stateless and keeps no application state of its own.

Security considerations

Applicant data is collected in onboarding and KYC. Later stages receive the outcome they need rather than a fresh copy of every document. Access to an application is limited to the stage working on it.

Resilience and fault tolerance

A failed check does not discard the application. The record keeps the last completed stage so the journey can resume. Calls to an external check use a timeout, and the stage stores the outcome it received.

Cloud-Native Application Architecture

A reference shape for a Java service on containers. The process is stateless. The platform runs the image, and state lives in a managed store.

Image delivered to the platform

Generic cloud-native shape. It is not a cloud-account or cluster map.

Architecture overview

A client calls ingress, ingress calls a healthy copy of a stateless service, and the service uses a managed store. A pipeline delivers an immutable image to the container platform that runs those copies.

Problem statement

A service that keeps session state, local files or machine-specific configuration cannot be replaced or scaled by starting another copy of the same image.

Design principles

  • The application process is stateless.
  • State lives in a managed store.
  • The deployable unit is an immutable image.
  • Configuration stays outside the image.
  • A health check decides whether a copy receives traffic.

Components and responsibilities

  • The client calls ingress only.
  • Ingress routes to a healthy copy.
  • The service handles the request and holds no local session.
  • The platform runs and replaces copies.
  • The pipeline builds and delivers the image.

Request and data flow

The request moves from the client to ingress to one copy of the service. The service reads configuration from the platform and state from the managed store. Separately, the pipeline builds an image and the platform starts that image. The service does not deploy itself.

Technology choices

Java and Spring Boot for the service, Docker for the image, Kubernetes for the platform, AWS as the cloud, and Jenkins with CI/CD for the pipeline. These are tools from my toolkit. The diagram is not an account layout.

Scalability considerations

More copies of the stateless service can be added, and ingress spreads requests across them. The managed store is shared by every copy, so its capacity is the limit to plan for. Sessions are not stored on local disk.

Security considerations

Ingress is the public entry. The workload uses an identity issued by the platform rather than a long-lived key baked into the image. Store credentials come from the platform. Images are produced by the pipeline.

Resilience and fault tolerance

The platform replaces a copy that fails its health check. More than one copy means a single process failure does not remove the service. The service uses a timeout toward the data store so a slow dependency does not pile up work.

Event-Driven Architecture using Kafka

A reference pattern for work that continues after the first service has accepted it. The producer publishes a fact. Consumers process that fact at their own pace.

Select a component. Arrows show the event moving from the producer to a consumer.

Component

Select a component

Select a component to see its responsibility. Connected components and arrows stay highlighted.

Generic Kafka pattern. It is not a production topic list or cluster design.

Architecture overview

A producer writes an event to a Kafka topic. Independent consumers read that topic, update their own services, and commit their own offsets. An event that cannot be processed is written to a dead-letter topic.

Problem statement

A request that must update several downstream capabilities becomes a chain of synchronous calls. One slow consumer delays the caller, and adding a consumer means editing the producer.

Design principles

  • The producer publishes a fact, not a call to a named consumer.
  • The topic is the contract.
  • Each consumer keeps its own pace and its own offset.
  • Handling an event is safe to repeat, or the consumer records that it was already handled.
  • A failed event has a defined place to go.

Components and responsibilities

  • The producer publishes after its own work is accepted.
  • The topic stores the event for every subscriber.
  • The consumer applies the event and commits progress.
  • The downstream service owns the side effect.
  • The dead-letter topic holds events that cannot be applied.

Request and data flow

A channel can still start the producer with a REST call. The producer writes the event and finishes. Each consumer reads the topic, updates its downstream service, and commits its offset. An event that cannot be applied is appended to the dead-letter topic so the partition is not blocked.

Technology choices

Kafka for the log, and Java services as the producer and consumers. REST remains the way a channel starts the work. Kafka is part of my toolkit. This study does not describe a production topic catalogue.

Scalability considerations

Consumers in a group share the partitions of a topic. A new kind of work is a new consumer, not a new call inside the producer. The topic can hold a burst that a consumer is not ready to finish immediately.

Security considerations

Producers and consumers authenticate to the cluster. A service reads only the topics it is allowed to read. The event carries the facts that the consumer needs, not a full customer record by default.

Resilience and fault tolerance

A consumer can stop and resume from its last committed offset. A poison message moves to the dead-letter topic so later events can proceed. The producer does not need the consumer to be up at the moment of publish.

Secure Digital Identity and Authentication

A reference boundary for OTP, face authentication and document retrieval. The business journey asks for a verification result. Provider internals stay outside the diagram.

Select a component. Arrows show the call moving from the journey to a verification method, and then to the result.

Component

Select a component

Select a component to see its responsibility. Connected components and arrows stay highlighted.

Generic identity boundary. UIDAI and DigiLocker appear only as the kind of verification already described in the portfolio. Their internal systems are not shown.

Architecture overview

The business journey calls one identity service. That service uses OTP, face authentication or document retrieval and returns a verification result. The diagram stops at the provider boundary.

Problem statement

A banking or lending journey may need more than one way to verify a person. Placing each provider call inside the journey spreads personal data and authentication logic across the product.

Design principles

  • The journey receives a result, not a biometric template.
  • One identity service owns the provider calls.
  • OTP, face authentication and document retrieval stay separate methods.
  • Personal data stays at the boundary.
  • The journey stores the outcome it is allowed to keep.

Components and responsibilities

  • The journey asks for a verification result.
  • The identity service selects and calls the method.
  • OTP, face authentication and document retrieval each do one check.
  • The result tells the journey whether to continue.

Request and data flow

The journey calls the identity service with the method it needs. The service performs OTP, face authentication or document retrieval through the external boundary. It returns a verification result. The journey continues from that result and does not see provider credentials.

Technology choices

Java, Spring Boot, REST and application security. The methods match the identity work already on this site: OTP, face authentication, DigiLocker-style document retrieval and UIDAI in the verification path. Provider internals are out of scope.

Scalability considerations

The identity service holds no session between calls and can run as more than one copy. Provider calls are the constrained dependency, so the service limits how much work it sends them. Document retrieval does not have to scale the same way as OTP.

Security considerations

The journey does not see provider credentials. Biometric input stays in the authentication method and is not written into the application record. Logs can carry a correlation id without the secret or the biometric. Only journeys that need a result can call the service.

Resilience and fault tolerance

If a method is unavailable, the service returns a failed verification for that method. The journey can offer another method it already supports. A timeout bounds the wait, and an unknown result does not complete the application.

    Microservices vs Monolith: Choosing the Right Architecture

    ×

    The useful question is which shape fits the team's ability to change, operate and own the system. A current diagram is not an architecture decision.

    Problem and context

    A single deployable application becomes hard to change when several teams edit the same codebase and every release carries unrelated risk. Splitting too early creates a distributed system before the domain boundaries are understood. The two failures are expensive in different ways: one couples the release, the other multiplies the ways a request can fail.

    Architecture approach

    Start from the business capabilities and how often each one changes. A modular monolith, with firm module boundaries and one deployment, is a sound architecture when one team owns the product and the domain is still moving. Microservices are justified when a capability needs its own deployment, its own scale profile, or a hard ownership boundary. The module boundary should exist in the code before it exists on the network.

    Key considerations

    • A network call is a new failure mode. It is not a free abstraction over a method call.
    • Data ownership has to follow the service boundary. A shared database recreates the coupling the split was meant to remove.
    • Each service adds a build, an environment, a trace and someone who is on call for it.
    • More than one team must be able to release without a shared release train, or the operational split has no delivery benefit.

    Trade-offs

    A monolith is simpler to debug, to wrap in one transaction, and to test end to end. It couples the release cadence. Microservices isolate change and scale, and they move consistency, latency and operations onto the team. A modular monolith keeps local transactions and still lets a module be extracted later, once its interface has settled.

    Practical recommendations

    • Draw the domain boundaries first and enforce them in review, even inside one repository.
    • Extract a service when its change rate or scale is clearly different from the rest, not because the diagram looks current.
    • Give the extracted service a stable API and its own data store.
    • Revisit the choice. An early split can be folded back, and a later split can be planned from a module that already has a boundary.

    Designing Resilient Banking Applications

    ×

    A banking channel has to fail in a way the customer can understand. Resilience is the design of that failure. It is not a claim that dependencies never fail.

    Problem and context

    Account enquiry, payments and identity checks depend on other systems. A slow or failed dependency will hold threads, retry work that must not be repeated, or show the customer an ambiguous result. In a banking journey an ambiguous result is a worse outcome than a clearly stopped step.

    Engineering approach

    Give every outbound call a timeout. Retry only an operation that is safe to repeat, and bound the attempts. Use a circuit breaker so a dependency that is already failing stops receiving traffic for a short period, then allow a few trial calls. Make a write idempotent, especially a payment or a stage change in an application. For each journey, decide what the customer sees when a dependency is down: a completed read from a store you trust, a pending outcome, or a stopped step.

    CircuitBreakerConfig.custom()
    .failureRateThreshold(50)
    .slidingWindowSize(20)
    .waitDurationInOpenState(Duration.ofSeconds(20))
    .permittedNumberOfCallsInHalfOpenState(5)
    .build();

    These settings illustrate the decisions: how many calls define failure, how long the dependency is left alone, and how it is probed again. They are not a production baseline.

    Key considerations

    • A timeout has to be shorter than the caller's own timeout, or the failure simply moves upstream.
    • A retry against a payment that is not idempotent can create a second instruction.
    • A bulkhead stops one slow dependency from taking the whole thread pool.
    • The system of record has finite capacity. Channel retries can become a load problem of their own.

    Trade-offs

    A short timeout protects the channel and can fail a call that would have succeeded a moment later. An open circuit fails fast and will also reject calls after the dependency has recovered, until the half-open probe succeeds. An idempotency key needs storage and a contract the caller must send.

    Practical recommendations

    • Write down the customer outcome for each dependency failure before tuning any threshold.
    • Store an idempotency key on any instruction that moves money or advances an application stage.
    • Do not retry a call that has no timeout.
    • Exercise the failure path. A breaker that has never opened is an untested design.

    Security · 2 min read

    API Gateway and API Security

    ×

    The gateway is the public entry. It is not the only place a call is allowed to mean something.

    Problem and context

    Channel applications need one place for authentication, request limits and routing. If that edge is treated as the only security control, the services behind it trust a network position. Any caller that can reach a service directly inherits the customer's authority.

    Architecture approach

    The gateway authenticates the caller, applies a coarse limit, and routes to the service that owns the capability. The service checks that this caller may perform this action on this resource. A token is validated. It is not decoded and then trusted because it looks well formed. Service-to-service calls use a workload identity. Customer data and credentials for a downstream system stay in the service that needs them.

    Key considerations

    • Authentication answers who is calling. Authorization answers what they may do.
    • A gateway outage is a channel outage. It needs more than one instance and a health check.
    • A rate limit protects the system of record as much as it protects the edge.
    • Gateway logs must not store secrets, tokens or a full personal payload.

    Trade-offs

    Checking authorization in every service is more work than checking it once at the gateway, and it is the control that still holds when a service is called from inside the network. Mutual TLS between services is a strong control, and it is operationally heavier than assuming the private network is enough.

    Practical recommendations

    • Terminate the public entry at the gateway. Keep service ports off the public network.
    • Pass an identity to the service. Do not pass a password or a long-lived secret.
    • Authorize the business action in the service that owns the data.
    • Load credentials from the platform at runtime. Keep them out of the image and the source repository.

    Integration · 2 min read

    Event-Driven Architecture with Kafka

    ×

    Kafka is a good fit when the producer should publish a fact and continue, and each downstream capability can catch up on its own.

    Problem and context

    A request that must update several downstream capabilities becomes a chain of synchronous calls. One slow consumer delays the caller. Adding a new consumer means editing the producer. The caller also becomes responsible for a result it does not own.

    Architecture approach

    The producer publishes a fact to a topic after its own work is accepted. Consumers read that topic independently, apply the change in their own service, and commit the offset after that work succeeds. The topic is the contract. A consumer that cannot process an event writes it to a dead-letter topic so the rest of the partition can continue.

    props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
props.put(ProducerConfig.ACKS_CONFIG, "all");

// Consumer: apply the change, then commit.
// A commit before the side effect can lose the event.

    Key considerations

    • The event carries the facts the consumer needs. It does not carry a full customer record by default.
    • In the usual configuration a record can be delivered more than once. The consumer either applies it safely twice or records that it was already applied.
    • Order is guaranteed within a partition, not across the topic.
    • The producer treats the event as published only after the acknowledgement it asked for has arrived.

    Trade-offs

    The caller can return before every downstream effect has finished. That shortens the caller's wait and removes a single combined answer. Consumers can lag, and the business has to accept a pending outcome. A step that needs an immediate answer from several parties should stay a request.

    Practical recommendations

    • Name the topic for the fact, not for the current consumer.
    • Commit the offset after the side effect, not before it.
    • Keep a dead-letter topic and a way to inspect what landed there.
    • Version the schema so a new field does not break a consumer that was written earlier.

    Redis Caching Strategies

    ×

    A cache is a freshness decision. The key, the TTL and the invalidation rule matter more than the product name.

    Problem and context

    A read path that always hits the system of record spends capacity on data that changes rarely. A cache added without an invalidation rule also serves data the business no longer considers current. Both outcomes come from treating the cache as an optimization bolted on at the end.

    Engineering approach

    Use cache-aside for a read the application understands. On a miss, load from the source of truth and store the value with a TTL. On a write, update the source of truth and then delete or replace the cache entry. Do not cache an authorization decision for longer than you are willing to honor a revoked one. Do not keep the only copy of a payment instruction in the cache.

    Value cached = cache.get(key);
if (cached != null) {
    return cached;
}
Value loaded = repository.load(id);
cache.set(key, loaded, Duration.ofMinutes(5));
return loaded;

    Key considerations

    • A TTL bounds staleness. It does not replace invalidation when the record changes.
    • A missing key and a stored empty result are different. Caching a miss can also hide a record that was created a moment later.
    • A popular key that expires can send many callers to the database together. One loader, or a short lock around the load, prevents that stampede.
    • Redis is another dependency. Decide, per use case, whether a Redis failure falls back to the source or fails the call.

    Trade-offs

    A longer TTL reduces load and widens the window of stale reads. Invalidating on every write keeps the cache closer to the source and adds a round trip to the write path. A service that cannot run when the cache is down has made the cache a critical dependency.

    Practical recommendations

    • Put the identity of the query in the key, not a generic name shared by several screens.
    • Set a TTL on every entry.
    • Delete the key when the underlying record changes.
    • Look at the hit rate before adding a second cache. An indexed read that is already cheap may not repay the complexity.

    Platform · 2 min read

    Kubernetes for Enterprise Applications

    ×

    Kubernetes is useful once a service can be replaced by starting another copy. The platform does not make a stateful process stateless.

    Problem and context

    A Java service that stores sessions on local disk, or that is configured by files edited on a particular server, cannot be scaled by running a second copy. An enterprise runtime has to start that copy, send traffic only when it is ready, and stop sending traffic when it is not.

    Architecture approach

    Build an immutable image in the pipeline and run more than one replica. Keep state in a managed store. A readiness probe tells the platform that this process can take a request. A liveness probe is reserved for a process that is stuck and should be restarted. Configuration and credentials come from the platform, not from the image.

    readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080

    Key considerations

    • Readiness and liveness answer different questions. A database the service cannot reach should fail readiness. Restarting the process will not fix the database.
    • Resource requests tell the scheduler what the replica needs. A limit chosen without a measured baseline can kill a healthy process.
    • A rolling update needs room to start a new replica before the old one stops.
    • Namespaces, network policy and a workload identity are the controls that make a cluster suitable for more than one team.

    Trade-offs

    Kubernetes gives a standard way to deploy, scale and replace a service. It also asks the team to operate probes, resources, rollouts and cluster add-ons. A single long-lived virtual machine is simpler until the service must scale or be replaced without someone logging on to a host.

    Practical recommendations

    • Remove local session state before moving the service.
    • Start with a readiness probe, a resource request and a rolling update.
    • Keep the liveness check cheap, and independent of downstream systems.
    • Give the workload an identity. Keep cloud credentials out of the image.

    Database Design and Scalability

    ×

    A larger server postpones a design problem. Ownership, indexes and the read path decide whether the database can carry the product.

    Problem and context

    An application database becomes the constraint when every feature adds queries to the same tables, reporting runs on the transactional store, and nobody owns the schema. Buying capacity treats that as an infrastructure issue. It returns as soon as the next unowned query arrives.

    Engineering approach

    Model data around the capability that owns it. Another module reaches that data through an API or a query the owner provides, not through the owner's tables. Index the queries the application actually runs. Keep a transaction short and inside one ownership boundary. Move reporting to a replica or a separate store when it competes with customer transactions. Partition or archive a table when its size is the measured problem, not when a diagram suggests it.

    select id, status, updated_at
from application
where (updated_at, id) < (:cursor_time, :cursor_id)
order by updated_at desc, id desc
fetch next 50 rows only;

    A keyset page stays stable as the reader moves forward. A large offset asks the database to walk rows it will throw away.

    Key considerations

    • A composite index helps when the leftmost columns match the filter and the sort. An index that matches no query is only a write cost.
    • Pagination needs a stable order. Offset pagination slows down as the page number grows.
    • Constraints protect integrity inside one database. Across services, integrity is an identifier, an event and a reconciliation, not a distributed transaction by default.
    • Connection pools have a ceiling. More application replicas can exhaust the database before they exhaust CPU.

    Trade-offs

    Normalization keeps a fact in one place and can add joins to a hot read. A controlled copy, owned by the service that reads it, makes that read local and has to be updated when the source changes. Strong consistency is straightforward inside one database, which is a reason to settle ownership before splitting data.

    Practical recommendations

    • Name an owner for each schema.
    • Add an index for a known query, and remove indexes nothing uses.
    • Take reporting off the primary once it contends with customer transactions.
    • Split data along an ownership boundary, not along a table that two features happen to share.

    Delivery · 2 min read

    CI/CD and DevOps for Microservices

    ×

    Independent deployment is real only when the artifact that was tested is the artifact that runs.

    Problem and context

    A service that can be released on its own still fails as a product when the build is manual, the tests run on one developer's machine, or the image that was tested is not the image in the environment. A rebuild between environments is a chance for the released bits to differ from the tested bits.

    Engineering approach

    Give each service a pipeline. The same commit produces one artifact. Compile and unit test, run the integration tests the service can own, build an image, and deploy that image to an environment that is not production. Promote the same image onward. Configuration changes by environment. The binary does not.

    Key considerations

    • A test that needs every other service to be up will be skipped or will block the pipeline. Test the service against its own contract, and keep a smaller end-to-end check for the journey.
    • A schema change travels with the service that owns it, and it has to be safe while an older replica is still running during a rollout.
    • A failed pipeline stops promotion. Bypassing it is a conscious decision.
    • Secrets come from a credential store. They are not written into the repository or an image layer.

    Trade-offs

    A strict pipeline slows the first appearance of a change in an environment and shortens the distance from a defect to a known build. A shared pipeline for many services is easier to start and couples their release. A pipeline per service matches independent deployability and needs a shared set of steps so each team is not maintaining a private copy of the same script.

    Practical recommendations

    • Build once. Promote that image.
    • Keep the main branch in a state the pipeline can deploy.
    • Version the schema change with the service change.
    • Make the pipeline the path to production.

    Operations · 2 min read

    Observability: Logs, Metrics and Tracing

    ×

    Logs, metrics and traces answer different questions. A shared identifier is what lets the three of them describe one journey.

    Problem and context

    In a single process, a stack trace is often enough. Across a gateway, a domain service and a database, the same request produces three partial stories. Without a shared identifier, an incident becomes a search through files that cannot be joined.

    Engineering approach

    Logs explain one event. Metrics show a rate, an error ratio or a duration over time. A trace shows the path of one request across processes. Put a correlation id on the request at the gateway and carry it on every downstream call. Log it on every line for that request. Publish a small set of service metrics: request rate, error rate and latency. Trace at the boundary where a request leaves a process.

    MDC.put("traceId", correlationId);
log.info("payment instruction accepted, instructionId={}", id);

    Key considerations

    • A log line without the correlation id cannot be joined to the rest of the journey.
    • A high-cardinality label, such as a customer id on every metric, will overwhelm the metrics store. Identifiers belong in logs and traces.
    • Alert on a symptom the customer feels, such as an error rate or a stopped journey. A log line is not an alert.
    • Personal data and secrets do not belong in logs. Log the decision and an identifier.

    Trade-offs

    Tracing every method is detailed and expensive. Tracing at service boundaries is usually the useful cut. Structured logs are easier to query and harder to read as raw text. A dashboard that shows only CPU can stay green while a business journey is failing.

    Practical recommendations

    • Create the correlation id at the edge and pass it through.
    • Alert on a few service-level symptoms.
    • Keep a per-service view of rate, errors and latency.
    • After an incident, check whether the three signals would have found it. Add the one that was missing.

    Leadership · 2 min read

    Technical Debt and Architecture Governance

    ×

    Debt needs an owner. Governance needs to arrive while the expensive decision can still be changed.

    Problem and context

    Technical debt becomes a surprise when it lives only as a complaint in a retrospective. Governance becomes a delay when a committee approves a diagram after the code is written. One hides the cost. The other arrives too late to change it.

    Approach

    Record a debt item as work that was deliberately deferred: what was left undone, why, and what event will force the team to pay it. Give it an owner and a review date. Use governance for the boundaries that are expensive to reverse: data ownership, a public API, a security control and the deployment unit. A short architecture decision record is enough. It states the context, the decision and the consequences.

    # ADR 014 — Keep the journey synchronous at the API
Status: Accepted
Context: The channel needs one outcome before the customer continues.
Decision: The API waits for the stage that owns the answer.
Consequences: The caller holds a timeout. Later stages can still
be asynchronous once that outcome is stored.

    Key considerations

    • Debt with no trigger will not be paid. Tie it to a change that becomes unsafe if the debt remains, or put it on a schedule.
    • A standard earns its place when it ends a repeated argument: how a service is exposed, how an event is named, how a secret is stored.
    • Review the boundary. A review of document formatting does not change the design.
    • An exception needs an expiry. A permanent exception is an unwritten standard.

    Trade-offs

    A light process lets teams move, and a boundary violation can go unnoticed until it is expensive to undo. A heavy process catches more and often arrives after the design has been built around the wrong constraint. The useful weight follows how hard the decision is to reverse.

    Practical recommendations

    • Write an architecture decision record for a choice another team will have to live with.
    • Track debt as items with an owner, not as a theme in a slide.
    • Review APIs, data ownership and security controls before build, while the decision is still cheap.
    • Expire exceptions. If the exception is still needed at the expiry, renew it in writing or change the standard.
